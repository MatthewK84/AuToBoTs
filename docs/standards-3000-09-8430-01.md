# Standards binding: DoDD 3000.09 and DoWI 8430.01

This file is the acceptance gate for code in this repository. No application code exists yet. A pull request that adds code without the evidence named here does not meet either issuance. This file is not a certification, an authorizing-official signature, or a claim of compliance.

## DoDD 3000.09, Autonomy in Weapon Systems, 25 January 2023

Cleared for public release. It governs autonomous and semi-autonomous weapon systems. It excludes autonomous systems that are not weapon systems. This repository does not implement a weapon, a fuze, or a release actuator. The commit, abort, grant, and indication path is written so that if a program uses it inside a weapon system, that path can satisfy the directive's design rules.

Binding rules for that path:

- Operators exercise judgment over use of force. A commit requires a signed grant. Absence of a grant inhibits. Issues #44, #45, #179.
- Engagement stays inside the commanded time and place. The grant window, fence hash, and coast-quality inhibit are that constraint. If they will not be met, commit terminates or waits for input. Issues #44, #184, #187.
- Terminate or obtain additional input. Abort of a commit already sent is #183. A dialect with no abort message stays a residual, not a pass.
- Human-machine interface shows what the operator must do and what the system will do. Issues #57, #58.
- Software is verifiable, auditable, and explainable. The tick log, reason codes, and replay are that record. Issues #24, #25, #147.
- V&V and realistic T&E are required before fielding. SITL claims are labeled as not operational test. Issue #73. This repository cannot perform OT&E.

## DoWI 8430.01, Accelerated Mission Software, 8 September 2026

Cleared for public release. It applies to software across the lifecycle, including national security systems. It is the binding instruction for how this code is built, not for how a weapon is employed.

Binding rules for every crate:

- Machine-readable evidence of composition, build integrity, and application security is a condition for operation. Section 3.5.a. Issues #188, #189.
- An SBOM is generated and maintained. Section 3.5.b. Issue #190.
- Builds are secure, automated, and observable, from trusted sources, protected from tampering. Section 3.5.c. Issues #63, #189.
- Integrated continuous T&E produces evidence of effectiveness, suitability, and survivability. Section 3.5.d. Issues #30, #73, #190. SITL is not OT&E.
- Logging does not leak sensitive information. Section 3.5.f. Issue #191.
- Developers remain accountable for AI-generated or AI-modified code. It gets the same review and security testing as handwritten code. Section 3.6. Issue #192.

## What a code change must show

1. No path constructs a release, arm, or fuze command.
2. Commit can be inhibited by grant, phase, coast, estimator, energy, traffic, no-strike, and pilot override.
3. A fault maps to Inhibit or Revert, never to a quieter Pass.
4. The diff includes or points at an SBOM and a build record once #188 and #189 exist.
5. AI-assisted edits name the reviewer in the pull request once #192 exists.

Until those evidence issues are implemented, code may be written and tested. It may not be described as meeting 8430.01 or 3000.09.
